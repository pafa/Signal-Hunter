重大事件研究与交易系统 · 规则设计 v0.5

重大事件发现 · 多因素聚合 · 历史追踪 · 人工批准 · 持仓复核

更新：2026-09-24。本文是可审阅的系统设计；实现状态以 BACKLOG.md 为准。主屏已有全球公司自动关注和 100 万 USD 结构演练账本，申请、本人审批、拒绝、费用/资金核算与人工持仓复核可用。真实行情撮合、自动全文研判、持续监控与策略有效性仍未完成或验证。

1. 系统要回答的六个问题

  1. 发生了什么新变化，系统是什么时候首次知道的？
  2. 相比过去，变化的体量、持续性、业务意义与市场预期差是什么？
  3. 单个事件是否值得优先核验；多条弱线索是否共同改变一条产业假设？
  4. 影响通过什么业务关系传导到哪家公司，收益由谁获得、损失由谁承担？
  5. 什么条件下观察、申请买入、增仓、减仓或退出；预计验证多久、持有多久？
  6. 持仓后原逻辑是否仍成立；实际结果是否支持升级研究方法？

最终输出是可证伪的交易假设。重大事件、利好、可买、能成交、最终赚钱是不同判断，必须逐项成立。

2. 内容处理：两级筛选与一个长期主题库

入口不局限为一条 RSS。Reuters 仍是当前新闻入口；官方公告、产品技术说明、榜单、公司披露、经营指标可以作为有来源的证据补入。本轮只自动接入 Reuters 聚合标题，官方案例是人工核验后回溯整理；尚未自动采集所有这些来源。

第一级对每条新标题运行本地规则，输出「优先核验 / 主题线索 / 常规资讯」。保存命中规则、股票实体、事件阶段、标题版本与处理时间。常规资讯只保存、索引，可人工提升；不会每条都调用深度模型。控制权变化、产品排名突破、生态开放或封禁、存续风险、政策准入变化为初始规则族。规则只解释“为什么值得看”，不认定为真实重大事件。

第二级只对候选及现有主题的实质增量开展深入研判。规划输入：有权读取的原始材料、主体与业务关系、过去版本、支持与反向证据、当时行情快照。规划输出采用结构化字段，不允许仅给一段看涨文字。没有全文时保留 headline-only；不能用模型记忆补造事实。

长期主题库允许新闻单独不重大，但合起来改变一个机制判断。新线索先找到主题，再指出它影响哪一段因果链、是独立证据还是重复传播、改变了哪一条旧判断。现在支持规则提示主题与人工关联；跨语言语义检索、自动聚类和自动反证检索仍待接入。

3. 什么叫重大：结构化证据，不先发明一个总分

维度必填问题可用原始量未知时处理
新颖性新事实、阶段跃迁还是旧叙事复述？新旧版本差异、首次公告时间标“增量未确认”
相对体量相对公司原有业务是否足够大？资产 / 收入 / 利润 / 用户占比不从绝对金额推定重大
持续性暂时波动还是长期结构变化？榜单持续、留存、合同期、审批阶段保留时间假设
机制为什么会改变需求、成本、竞争或盈利？因果环节与每段证据缺环不得跳过
可信度原始来源是否可靠、是否被更正？官方文件、独立核验、转载关系降为待核验
预期差市场此前是否已经知道或计价？历史披露、估计修订、事前价格与成交变化不把热门等同于未计价
可交易性对应证券、时效、流动性、规则是否允许？行情与交易状态、可卖量不能生成可执行成交

候选优先级建议：P0 为持仓逻辑可能被推翻或存续风险，先核验；P1 为控制权、商业模式或关键业务阶段跃迁；P2 为与在研主题相关的弱增量；P3 为常规保存。这里是研究分流顺序，不是上涨概率。当前只有标题层的分流代码，完整体量和预期差判定需数据与人工标注。

后续训练重大性模型时，把“是否值得提前关注”“是否改变公司价值”“是否有可交易预期差”拆成三个标签。先收集人工判断、理由、误报和漏报，不把股价事后上涨直接当成重大新闻标签。

4. 多因素聚合算法

  1. 提取主体、产品、动作、事件阶段、地域、数值、时间及原始来源。
  2. 按主体关系与机制关联检索旧主题；同词不等于同事件，例如 Muse 产品与同名乐队分开。
  3. 先去重文章，再追溯原始事实来源；十篇转载同一公告只能算同一事实，不算十个独立验证。
  4. 将线索归入采用、运行机制、生态、供给、采购、财务、限制等证据族，并关联明确的因果环节。
  5. 指定支持、反对、背景或待核实。产品热门只能支持采用环节，不能填补盈利证据缺口。
  6. 检查替代解释：营销拉新、补贴、短期事件、统计口径、基数、技术效率或供给约束。
  7. 输出证据覆盖、缺失环节、共同来源与冲突；生成下一项最能改变判断的核验任务。
  8. 保存一个新研究版本。新版本解释“相对旧版本改变了什么”，不覆盖旧预测。

当前可执行部分是规则路由、结构化人工聚合、来源主体去重、缺环提示、证据核验及版本保存。来源独立性仍是保守的主体级去重；不同机构引用同一原始数据时还需要人工合并。不得声称已经具备自动深度语义分析。

5. CPU 主题：把一年假设拆成可检验的链条

Agent 采用和任务量 → CPU 执行负载 → 闲置容量消耗 / 新采购 → 供应商订单与份额 → 利润和现金流 → 估值与交易回报。

研究量纲：总 CPU 需求近似取决于活跃 Agent 数、每个 Agent 的任务量、单任务 CPU 秒、并发峰值和有效利用率。服务器采购还要扣除闲置容量，并考虑云厂商自研、租赁与扩容方式。这里只是分解方法；当前没有这些连续测量数据，不能计算精确需求增长率。

Meta 的技术说明显示 Muse 使用独立 Linux 虚拟机，执行任务需要 CPU、内存和存储。这支持运行机制，不等于证明全球 CPU/GPU 配比已经反转。Meta 技术说明 ↗

历史对照：Arm 在 2026-03-24 已宣布面向 Agent 的 CPU，2026-09-08 又发布平台进展。已有产业叙事可能早被讨论；本次必须寻找相对旧预期的采用、采购或盈利增量。Arm 3 月公告 ↗；Arm 9 月公告 ↗

AMD 官方将 EPYC 定位为 Agent 相关工作负载方案；属于厂商产品主张，不能替代独立采购数据。AMD 产品说明 ↗

“持续一年”保存为用户初始产业假设，不是模型预测。按采用、扩容、订单、财报分别验证，可以提前失效或延长。观察节奏建议为：产品指标按周、基础设施采购按公告/季度、股价与成交按分钟。具体常驻运行与通知节奏需另行确定。

可能的反证包括：CPU 秒/任务显著下降；任务活动未形成持续留存；闲置容量足够；云厂商自研吸收采购；价格竞争吞噬增量利润；GPU 推理同时增长；整个预期已被市场计价。不能把所有“以 CPU 为核心”的公司一视同仁。

Grok 迭代、Linux 复兴和 Company Agent 增长先作为用户线索；具体版本、采用指标、时间序列和对 CPU 的归因尚未核验，不冒充既成事实。

7. 事件追踪与历史对照

每个事件保留 event_id、主题、主体关系、已知时间、发生时间、来源版本、当时可用材料、事件阶段、研究版本、因果边、旧判断、变化理由及反证。研究保存不可变快照，后续新增证据、人工核验、改假设或归档都产生新版本。

来源时间线回答“过去发生过什么”；研究版本回答“系统当时知道什么、怎么判断”。回溯补入的旧公告必须保留今天的 first_seen，不能把发布日期当系统当时已知时间。

规划中的自动历史检索分三层：同一事件的前序阶段、同一公司的相似事件、同类机制的历史对照。对照样本需包含失败、无信号和反方向案例。召回结果附相似之处与关键差异，禁止把历史收益机械套到本次。

增量对照输出：新增事实、修订事实、未变事实；支持/削弱哪条因果边；是否影响价格触发、期限、仓位计划或退出条件。内容修正也必须把原错误留在审计历史。

8. 交易假设与执行状态机

研究状态：线索 → 待核验 → 在研 → 证据冲突/补证 → 观察或形成申请 → 归档；允许恢复。研究版本不断追加。

计划中的正式交易状态：草稿 → 待人工确认 → 已批准 → 等待可交易条件 → 委托中 → 部分成交/成交/取消/拒绝/过期。部分成交只影响已成交数量；剩余量继续保留。批准不等于成交。

申请必须包含：事件和获批研究版本、标的、方向（买入/增仓/减仓/清仓）、触发条件、失效条件、数量、限价与有效期、报价快照、费用/滑点口径、预计持有期、复核日期与审批指纹。

当前可从关联公司或持仓提交结构演练申请，由本人批准或拒绝。场景价格和固定 FX 与现场行情隔离，真实行情不进入场景净值。真实行情撮合与部分成交仍待实现，旧演示视图继续独立保留。

9. 持仓过程中的四种复核

触发方式具体检查结果
新事件到来是否涉及持仓公司、上下游、监管或原假设的关键环节？不变 / 补证 / 减弱 / 失效
临时重大利空原逻辑是否被确认推翻？是否必须优先处理？紧急核验或退出申请
价格 / 成交异常是否触发已批准的风险条件？是否行情错误、复权或休市？复核，不用价格反推新闻事实
到期 / 定时预期催化是否发生、研究期限是否到期、财报是否兑现？延续、改假设或退出申请

演练持仓绑定初始化或获批研究版本，新研究不重写原买入原因。当前可保存临时复核、显示研究版本变化，逻辑失效可打开拟减仓表单；持续自动持仓监控尚未接入。

10. 特大利空时怎么卖

可执行门禁顺序：有关联持仓 → 原逻辑可能失效 → 核实证据 → 用户明确减仓/清仓数量 → 检查可卖数量 → 核验报价新鲜度 → 核验开市、停牌与流动性 → 生成绑定版本的退出申请 → 用户确认 → 正式模拟引擎校验并执行。

未经确认的标题进入最高优先级核验，不直接成交。清仓数量最多是该时点可卖数量；A 股等市场的可卖限制以后由市场适配器提供，不能仅用持仓总数替代。具体交易所规则与板块差异需要官方核验后实现，本轮不假定所有市场行为一致。

遇到停牌、价格限制或没有可成交对手盘时，状态是阻断/排队/未成交，而不是“已卖出”。恢复后重新验证剩余可卖量、行情、申请有效期和人批参数。旧行情、旧数量、旧证据或持仓版本变化会令原审批绑定失效。

分批退出未来需定义每批量、价差/流动性约束、最长等待、取消规则和用户允许的最差价格。没有这些参数时不自动推导一套算法；不能默认用无限滑点的市价单保证清仓。

当前 planExit 是纯函数门禁：返回 observe / verify / needs-parameters / blocked / awaiting-human / eligible-for-paper-engine，永远 automaticExecution=false。它测试决策顺序，不模拟流动性和成交。演练中的证据确认、新鲜度、开市与批准有效性是显式测试输入；不代表已接通真实市场状态或安全审批存储。正式账本实现后必须由服务端可信适配器产生这些输入。

11. 规则清单与可执行性

R01

保留当时信息

已实现

新闻原文首次获取与各修订版可用时间分开；证据引用冻结对应版本，回溯案例单独标注。

输入
新闻标识、标题修订、来源发布时间、系统首次获取时间、规则版本。
判定与动作
原文记录 firstSeen，各修订记录 revisionFirstSeen；证据 availableAt 取所引版本的实际接收时间，不沿用旧标题的可用时间。
输出与异常
新闻快照与处理时间；日期缺失保留未知，不补造成当时已知。
验收与有效性
已测回溯时间与 RSS 快照冻结；前向评估只使用决策时已收到的版本。
R02

先初筛，再研判

已实现

标题按并购、审批、临床、订单、供给、资本回报、政策等候选分流；区分传闻、拟议与否认，不命中允许人工提升。

输入
新标题、来源、证券别名、事件动作与阶段词。
判定与动作
按确定性规则分为 review / clue / quiet；存续风险、控制权或生态等实质变化优先核验，弱关联进入主题线索。
输出与异常
候选及命中理由、阶段、规则版本；所有结果 tradeSignal=false。quiet 可人工关联。
验收与有效性
已测常规、弱线索、重大候选和同名混淆；后续用冻结标注集测漏报、误报与处理延迟，不用当前命中数代表准确率。
R03

重大性不等于利好

部分实现

分别检查业务体量、预期差、持续性、可验证性和可交易性。当前规则只产生候选；R31 的主观证实概率不等于重大性或上涨概率。

输入
来源事实、公司业务基数、过去披露、市场事前预期与行情。
判定与动作
逐项回答新颖性、相对体量、持续性、机制、可信度、预期差、可交易性；未知单列，不折算成一个上涨总分。
输出与异常
重大性研究结论和待补数据；现仅实现标题候选，完整判定尚无执行器。
验收与有效性
待验收：同一新闻对不同公司得到不同影响解释；缺业务基数时不输出精确重大性概率。
R04

事实、观点与推论分开

已实现

官方资料、媒体报道、用户线索分层；标题和手填链接不自动升级为已确认事实。

输入
主张、来源、读取范围、核验者、支持或反对作用。
判定与动作
RSS 标题与手填内容先标 unverified；人工核验须提供依据，并追加版本。事实核验与投资推论分开。
输出与异常
primary / reported / reviewed / unverified 等证据属性；确认事实不等于确认股价方向。
验收与有效性
已测手填链接不能自升为已确认、核验可撤回且保留旧版本；核验准确率仍需抽样复审。
R05

聚合成因果链

部分实现

每条证据关联一个机制环节，并明确支持、反向约束、背景或待核实。跨新闻自动语义聚类待接入。

输入
主题因果链、证据、证据族、作用、来源主体。
判定与动作

输入

代码入口：triage.mjs 负责标题分流与证据覆盖；research.mjs 负责证据、人工核验和不可变版本；risk-rules.mjs 负责退出门禁；store.mjs 负责新闻/行情数据。research.test.js 覆盖错判边界、版本、重复证据和退出状态。

12. 怎样评估算法是否有效

第一层是内容质量：重大候选的人工相关率、重大事件漏报率、错误公司映射率、来源核验覆盖率、重复事件比例、相对首次公开信息的发现延迟。先建立含普通新闻、传闻、失败事件的标注集，冻结标签后比较。不能只挑四个成功案例。

第二层是推理质量：因果链是否完整、反证是否被纳入、有没有用未来资料、对同一证据是否重复计权；时间假设到期时兑现、延迟或失效的比例。模型输出概率前，必须用未参与调参的样本检查校准。

第三层是事件与价格：记录首次获取后 1 小时、1 日、5 日、20 日等固定窗口的原始与基准超额变化，窗口与交易日历须预先固定。它衡量价格响应，不是实际账户收益。

第四层是模拟成交：费用、滑点、币种、仓位、未成交、延迟审批、持有期和退出困难全部计入。报告净收益、最大回撤、胜负分布、尾部损失、换手、资金占用与未平仓估值。被拒绝/失效申请同样保留。

实验按时间分训练/验证/测试；围绕同一事件的相近窗口不能泄漏到两侧。采用固定基线（关键词初筛 + 人工判断）与候选规则并行；先做影子运行，再考虑批准替换。报告样本量、区间、不确定性和成本敏感性，不按短期盈利自动上线。

早发现实验只能用真实 first_seen 或明确标注的可用时间假设；本轮回溯案例不得纳入“提前发现”的有效样本。当前尚无足够前向样本，不能评价策略有无收益优势。

13. 按依赖推进的下一步

  1. 审阅这版研究工作台与 31 条规则，修正事件类别、重要性依据和术语。
  2. 保存连续真实新增样本，建立人工重大性、关系和反证标注；以误报和漏报改进初筛。
  3. 接入候选级内容读取、历史召回与结构化深度分析。付费模型不在当前免费范围内；模型或本地运行选择需要用户决定。
  4. 核验三市场交易规则并确认模拟资金、仓位、费用滑点、审批有效期、账户币种、盘前盘后范围和风险阈值。
  5. 建立正式事件—申请—模拟账本，再连接持仓复核与紧急退出申请。先做不可成交/部分成交/重复审批测试，再做前向模拟。
  6. 用户确定运行时段、常驻位置和通知方式后，才将风险监控升级为持续服务。

当前运行边界：仅本机进程运行时轮询；RSS 每 10 分钟，关注行情每 60 秒尝试更新；免费聚合的覆盖和延迟不承诺，行情供应商时区/延迟部分仍待核验。没有常驻告警或自动交易。

v0.7 修订：不确定性也是研究对象

传闻和未证实消息不隔离，不要求事实确认后才能研究或提交模拟申请。消息状态与支持/反对方向独立记录；主观证实概率绑定一个可检验主张及截止日，必须记录依据、若属实的业务与预期影响、若未兑现的反向风险。允许 20%、50%、70% 等估计，依据不足留空；不自动折算为股价上涨概率或仓位。每次修订、确认、否认与部分证实保留旧版本，后续用于校准；同源转载不能被当成多次独立支持。

主屏按持仓失效、关联反向线索、期限、申请版本等排序；未证实的反向线索同样提升持仓复核优先级。持仓已被本人判定逻辑失效时暂停相关新增买入，复核恢复后可继续；任何减仓都仍须本人批准。到期申请立即排除预算占用，并由维护任务追加历史记录。规则初筛与主观概率功能已接入；自动全文判断、概率校准、真实市场撮合仍未实现。
